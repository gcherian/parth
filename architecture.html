The Parth Blueprint

A microkernel with an event-driven backbone: a dumb, transactional kernel routes events between domain modules that each own their slice completely. This map reflects what's actually running in server/ today — verified against main.py, kernel/router.py, and every module's own docstring — not the aspirational roadmap alone.

Three layers, one contract

The kernel knows event types and a routing table — nothing about curriculum, psychology, or which LLM is behind tutor.runtime. Every module implements handle(event, ctx) → ModuleResult and an on_erase() hook for right-to-erasure.

The interaction.requested pipeline

This is kernel/router.py's live ROUTING_TABLE for /chat — every step is Sequential in practice, because all modules in one interaction share a single asyncpg connection (ctx.db), and Ollama's own latency dwarfs the pre/post-phase overhead anyway.

Phase 1 — pre-generation context buildsequential
moderation.ops→ learner.state→ curriculum.graph→ meaning.graph→ wonder.engine→ mag.memory
Phase 2 — generationcritical path, synchronous
tutor.runtime
Phase 3 — post-generationsequential
moderation.ops→ learner.state→ wonder.engine→ mag.memory→ practice.engine
Veto short-circuit: moderation.ops is the only module that can return ModuleResult(veto=True). The router checks ctx.moderation_ok after every phase and aborts the whole pipeline the instant it's tripped — the child gets a pre-approved safe message, not silence.
Idempotency: the orchestrator checks foundation.idempotency by request_id before doing anything. A retried request replays the cached response — no module runs twice for the same interaction.

All 20 modules

11 are registered with the kernel (main.py's _modules_list) and take part in routed events. The rest are FastAPI routers or services that sit beside the kernel — real, live code, just outside the event-routing contract.

learner.state's 18 live agents

modules/learner_state/agents/__init__.py::build_agent_registry() wires exactly 18 agents into the dispatch loop, dependency-ordered across 4 layers, each contributing to the 15 named learner dimensions (some dimensions are backed by more than one agent — see dimensions.py).

17 more files sit in the same directory, unwired: analogy_domain, attribution_style, chrono_pattern, cognitive_profile, confidence_calibration, curiosity_tracker, episodic_memory, family_context, knowledge_state, learning_speed, linguistic_register, misconception_map, motivational_profile, open_loop, productive_struggle, sessional_emotion, stress_signature. Not imported by build_agent_registry(), not dispatched, not distinguishable from the live 18 by directory structure alone — verify against __init__.py, not the file listing, before trusting a name. (confidence_calibration.py specifically is dead — its job is done instead by belief_coach.py, which writes the same table inline.)
lens/ sits next to this as a separate module: five read-only "portrait" computations — cognitive, affect, psychological, contextual, relational — exposed via /api/lens/{lens_name}/{learner_id}/run, distinct from the always-on agents above.

L1 — what's actually under everything

tutor.runtime's backend switch

Config.TUTOR_BACKEND — the only module in the system that knows an LLM backend exists at all.

ValueBehaviour
autoAnthropic (Claude) if ANTHROPIC_API_KEY is set, else falls back to local Ollama.
anthropicAlways Claude — cloud / investor pilot mode.
ollamaAlways local Ollama (gemma3:12b / llama3.2) — dev / offline, free, private.
Krishna Oracle (modules/krishna_oracle/oracle.py) is a second, asynchronous LLM tier: Parth (Ollama) answers every message; Krishna (Claude/GPT-4) reads a child's full trajectory every N interactions and writes strategic guidance Parth applies afterward — never in the critical request path, silently disabled with no API key.
